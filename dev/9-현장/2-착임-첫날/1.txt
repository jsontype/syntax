[착임 첫날 — 지도 그리기 프롬프트]
참조: 사전준비: 팀 리포를 전부 {{workspace}} 아래에 clone. 개인 노트 폴더 {{notes}} 를 리포 밖에 만든다. 1-사용법 노트의 "공통 전제"를 첫 줄에 붙인다
참조: 순서 1 → 7 이 하루 분량. 1·2·3 은 오전, 4 는 환경 구축하면서, 5·6·7 은 오후. 8 은 퇴근 전
참조: 목표는 "코드가 아니라 지도를 손에 쥐고 둘째 날을 시작하는 것". 이 날 코드를 고치지 않는다 ★

[1. 리포 전수 조사 — workspace 지도] ★★
용도: 착임 당일 1순위. 원형은 "이 팀에서 쓰는 모든 리포를 다 workspace 안에 정리해두고 있어. 전체적으로 정리해봐." — 아래는 그걸 산출물이 나오게 구체화한 것
---
{{workspace}} 안에 이 팀에서 쓰는 모든 리포를 clone 해두었다. 전체를 조사해서 {{notes}}/00-map/repos.md 에 "리포 지도"를 써라.
리포마다:
1. 한 줄 역할(무엇을 누구에게 제공하는가) — README·package.json·진입점으로 판단
2. 스택과 버전(언어·프레임워크·런타임·패키지 매니저·모노레포 도구) — lock 파일·engines 필드 기준
3. 실행·빌드·테스트·린트·배포 명령 — README 가 아니라 실제 스크립트·CI 파일에서 추출
4. 환경변수·시크릿 요구 목록 — .env.example·CI 변수 참조·process.env 검색. 값은 절대 적지 마라
5. 최근 90일 활동 — 커밋 수, 상위 기여자 3명, 가장 많이 바뀐 파일 10개(git log --since=90.days --name-only 집계)
6. 다른 리포와의 관계 — API 호출·공유 패키지·DB 공유·이벤트. 호출 URL·패키지명을 근거로
7. 문서와 실제의 괴리 — README 의 명령이 실제로 없거나 다른 것
마지막에:
- 리포 간 의존도 mermaid 그래프 1장(프론트 → BFF → API → DB · 외부 서비스)
- "가장 중요한 리포 3개"와 이유(활동량·의존 수·장애 영향)
- 코드만으로 알 수 없는 것 10개(왜 이렇게 됐나·오너·금기)를 질문 형태로
---
기대 산출물: repos.md 1장. 둘째 날부터 모든 대화의 입력이 된다
주의: 리포가 20개를 넘으면 "활동량 상위 10개 먼저, 나머지는 한 줄 역할만" 으로 나눠 돌린다

[2. 요청 한 바퀴 — 아키텍처 1장]
용도: 1 이 끝난 직후. 대표 시나리오 하나를 끝까지 따라가 본다
---
{{workspace}} 의 리포들을 바탕으로, 대표 사용자 시나리오 하나({{예: 로그인 → 검색 → 주문 → 결제}})가 브라우저에서 DB 까지 갔다가 돌아오는 경로를 추적해 {{notes}}/00-map/architecture.md 에 써라.
- 각 홉마다: 리포·파일·함수, 프로토콜(REST·GraphQL·gRPC·큐), 인증 방식, 에러 처리, 타임아웃·재시도
- 환경(dev·stg·prod)별 차이: 설정 파일·인프라 코드(terraform·k8s·serverless·cloudflare)에서
- 배포 파이프라인: 트리거 → 빌드 → 테스트 → 배포 → 롤백. CI 파일 경로를 근거로
- 관측: 로그 포맷·메트릭·알람·에러 트래킹이 어디에 있고 무엇이 비어 있는지
- 시퀀스 다이어그램(mermaid) 1장
- "이 경로에서 가장 깨지기 쉬운 지점 3개"와 근거
---
주의: 시나리오를 내가 고른다. 모르면 리드에게 "가장 돈이 되는 화면 하나"를 묻고 그걸로

[3. 규약 추출 — 문서 vs 실제]
용도: 첫 PR 을 내기 전에 반드시. 문서가 없는 팀일수록 중요
---
이 팀의 규약을 두 축으로 정리해 {{notes}}/00-map/conventions.md 에 써라: (A) 문서에 적힌 것 (B) 실제 코드·git 이력에서 관찰되는 것. 둘이 다르면 표로 대조하라.
항목: 브랜치 전략·브랜치 이름, 커밋 메시지 형식(최근 200개 커밋 집계), PR 템플릿·크기(최근 PR 변경 줄 수 중앙값), 리뷰 규칙(CODEOWNERS·승인 수), 코드 스타일(lint·prettier·tsconfig·editorconfig), 폴더 구조·네이밍, 테스트 작성 방식(프레임워크·위치·커버리지 설정), 릴리스 주기·태그, 티켓 번호 규칙, 언어(커밋·PR·코멘트가 일본어인지 영어인지).
마지막에 "내가 PR 을 낼 때 지켜야 할 체크리스트 10줄"을 만들어라. 팀 문서가 없으면 (B) 만으로 만들고 '관찰 기반'이라고 표시하라.
---

[4. 환경 구축 — 막힌 곳이 곧 첫 PR]
용도: 셋업 문서대로 진행하면서 대화형으로. 가장 안전한 첫 기여(온보딩 문서 수정)가 여기서 나온다 ★
---
{{리포}} 의 셋업 문서대로 로컬 환경을 구축한다. 내가 명령을 실행하면서 막히는 지점(에러 전문)을 붙여넣을 테니, 매번 (1) 원인 가설 (2) 확인 명령 (3) 수정안 순으로 짧게 답하라.
해결될 때마다 {{notes}}/00-map/setup-log.md 에 "문서 n번째 단계 → 실제로는 무엇이 필요했나"를 한 줄씩 누적하라.
다 끝나면 그 로그로 (a) 온보딩 문서 수정 PR 초안(diff 형식 · 일본어 설명 3줄) (b) 셋업을 한 번에 돌리는 스크립트 초안을 만들어라. 스크립트는 팀 규약(3 의 conventions.md)의 언어·위치를 따르라.
---
주의: 문서 수정 PR 은 "틀린 것을 고쳤다"가 아니라 "제 환경에서는 이렇게 해야 됐습니다"로 쓴다. 문서 작성자가 옆자리일 수 있다

[5. 아픈 곳 지도 — 장애·핫픽스·핑퐁]
용도: 팀이 어디서 아파하는지를 git 이력으로. 3-상위1퍼센트 의 재료
---
{{workspace}} 전 리포의 git 이력에서 팀이 아파하는 곳을 찾아 {{notes}}/00-map/pain.md 에 써라.
- 최근 180일 커밋 메시지에서 fix·hotfix·revert·緊急·障害·不具合·修正·暫定 패턴 집계 → 파일·모듈별 빈도 상위 20
- 같은 파일이 짧은 간격(7일 이내)으로 반복 수정된 곳(핑퐁) 상위 10
- 변경 빈도 × 파일 크기(또는 복잡도)가 큰 핫스팟 상위 10
- 포스트모템·障害報告·incident 문서가 있으면 요약(원인 분류·재발 여부)
- CI 에서 자주 실패하는 잡·플레이키 테스트(워크플로 로그가 있으면)
각 항목에 "증상 → 추정 원인 → 확인하려면 누구에게 무엇을 물을지"를 붙여라. 추측은 추측이라고 표시하라.
---

[6. 사람 지도 — 누구에게 뭘 묻나]
용도: 질문을 엉뚱한 사람에게 하지 않기 위해. 평가가 아니라 영역 지도
---
{{workspace}} 전 리포에서 "누가 무엇을 아는가"를 {{notes}}/00-map/people.md 에 써라.
근거: CODEOWNERS, git shortlog -sn --since=180.days (리포·디렉터리별), PR 리뷰어 패턴(가능하면), 문서의 작성자.
출력: 사람별 — 주 영역(디렉터리·리포), 최근 활동량, 리뷰를 많이 하는 영역, 내가 물어볼 주제 / 영역별 — 1순위·2순위 담당자, 담당자 공백(최근 6개월 아무도 안 건드린 핵심 모듈 = 버스 팩터 0~1).
개인 평가·서열 표현은 쓰지 마라. 사실(활동 영역)만.
---
주의: 이 파일은 특히 밖으로 나가면 안 된다. 노트 폴더에만

[7. 질문 10개 — 리드용 5 · 멤버용 5]
용도: 1~6 을 읽고 코드로는 답이 안 나오는 것만. 질문은 모아서 한 번에 ★
---
{{notes}}/00-map/ 의 지도들(repos·architecture·conventions·pain·people)을 읽고, 코드만으로는 답이 안 나오는 질문을 10개 뽑아라.
조건: 각 질문에 "왜 중요한가(어떤 결정에 영향)"와 "누구에게(people.md 기준)"를 붙이고, 예/아니오로 끝나지 않게 열어 두고, 일본어 문장을 병기하라(丁寧語 · 전제 1줄 + 질문 1줄 · 간결).
우선순위: AI 이용 규정 → 금기(건드리면 안 되는 곳) → 오너십 → 현재 가장 아픈 곳 → 진행 중인 큰 변경 → 릴리스 일정.
리드 1on1용 5개 / 멤버 잡담용 5개로 나누고, 내가 이미 코드에서 확인한 사실을 전제로 깔아 "조사하고 왔다"가 드러나게 하라.
---

[8. 첫 5영업일 계획]
용도: 퇴근 전. 둘째 날부터 뭘 할지 정해두고 간다
---
{{notes}}/00-map/ 의 지도와 질문을 바탕으로 첫 5영업일 계획을 {{notes}}/90-journal/week1.md 에 써라.
하루마다: 오전(읽기·환경), 오후(작은 기여), 퇴근 전 기록(6-루틴 형식).
기여는 "안전한 첫 PR" 순서로: 온보딩 문서 수정 → 셋업 스크립트 → 린트·타입 에러 1건 → 테스트 없는 작은 유틸에 테스트 → 그 다음에야 기능.
각 PR 에 예상 변경 줄 수(150줄 이하)와 리뷰어 후보(people.md)를 붙여라. 5일째 오후에는 "문제 후보 10개"(3-상위1퍼센트 노트) 작업을 넣어라.
---

[첫날 금기 — 프롬프트 아님] ★
1. 코드를 고치지 않는다. 지도만 그린다
1. "왜 이렇게 했어요?"라고 묻지 않는다. "이 부분의 배경을 알려주실 수 있을까요(背景を教えていただけますか)"로
1. 지도의 결론을 팀에 공유하지 않는다. 아직 틀린 곳이 많다. 질문만 공유한다
1. AI 산출물을 그대로 믿지 않는다. 숫자는 직접 한 번 다시 센다(git log 한 줄이면 된다)
