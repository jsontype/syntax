[시스템 디자인 기초]
참조: 면접용이 아니라 실무 설계문서(design doc)를 쓰기 위한 골격

[전체 순서 ★★]
1. 요구사항 정리
  기능 요구(무엇을 하는가) / 비기능 요구(트래픽, 지연, 가용성, 비용)
  숫자로 적을 것: DAU, RPS, 데이터 크기, 읽기:쓰기 비율
1. 추정 (백오브엔벨롭 계산)
  QPS = DAU x 1인당 요청수 / 86400 (피크는 x2~x10)
  저장량 = 1건 크기 x 건수 x 보존기간
  대략 자릿수만 맞으면 됨. 계산 근거를 문서에 남기는 것이 목적
1. 설계
  API 정의 → 데이터 모델 → 컴포넌트 다이어그램 순
1. 트레이드오프 언어화
  "A 대신 B를 선택했다. 이유는 ~. 대가로 ~를 포기했다" 형식
  이 문장이 설계문서의 핵심 가치

[스케일링]
1. 수직 스케일링 (scale up)
  서버 스펙 올리기. 간단하지만 한계와 단일 장애점 존재
1. 수평 스케일링 (scale out)
  서버 수 늘리기 + Load Balancer
  전제: 서버가 stateless일 것 (세션은 외부 저장소로)

[캐시]
1. 위치: 브라우저 / CDN / 애플리케이션(Redis) / DB 내부
1. 전략: cache-aside(기본), write-through, write-back
1. 주의: 무효화(invalidation)와 TTL 설계가 본체
  "캐시로 해결"이라 쓰지 말고 hit rate 가정과 stale 허용 범위를 적을 것

[큐 (비동기 처리)]
1. 목적: 피크 흡수, 느린 작업 분리, 서비스 간 결합도 낮추기
1. 예: SQS, RabbitMQ, Kafka(스트림)
1. 대가: 즉시성 포기, 중복 처리 대비(idempotency) 필요

[DB 복제 / 샤딩]
1. 복제 (replication)
  primary(쓰기) + replica(읽기) 구성으로 읽기 분산
  대가: replication lag → 읽기 직후 자기 데이터가 안 보일 수 있음
1. 샤딩 (sharding)
  쓰기/용량 한계 돌파용. shard key 선정이 전부
  대가: cross-shard join, 재분배(resharding) 고통. 최후의 수단 ★

[CAP 골격]
1. 네트워크 분단(P)은 피할 수 없으므로 실질 선택은 C vs A
  C 우선: 은행 잔고, 재고 (일관성 깨지면 사고)
  A 우선: 타임라인, 좋아요 수 (조금 틀려도 서비스 지속이 중요)
1. 설계문서에는 "이 데이터는 어느 쪽인가"를 데이터별로 표기

[실무 설계문서 작성 팁]
1. 구성: 배경 → 요구사항 → 추정 → 제안 설계 → 대안과 트레이드오프 → 롤아웃 계획
1. 대안을 최소 1개 적고 왜 안 골랐는지 쓰기 (리뷰어가 가장 먼저 보는 부분)
1. 책으로 심화: 같은 폴더의 부록(데이터지향어플리케이션) 참조
